Added 2026-11-24 (Phase 5 upgrade). Each fact is from the page named in its heading, read on that date; **(unverified)** marks something that came through a model summary or was not on a page read. Use with `planner-playbook.md` (the plan format), `architect-playbook.md` (decomposition and drift) and `architect-reference.md` (broader craft).

## 1. Lint the plan before handing it back
`node scripts/plan-lint.mjs <plan.md>`. The consulting agent runs it and shows the output (the specialist has no shell). It checks the format the planner playbook already demands, mechanically:
- **FAIL:** a missing section (all twelve headings), a task line missing owns, depends, est, covers or done when, a `depends:` that names no task, a dependency cycle, two tasks in one phase owning the same file when they can run in parallel, a task over 8 hours, a Must requirement no task covers, a `covers:` entry that does not exist, an NFR with no number, a risk missing likelihood, impact, mitigation, contingency or owner, an ADR missing Context, Decision, Consequences or Alternatives.
- **WARN:** ordered tasks sharing a file, shared wiring (`package.json`, lockfiles, `migrations/`, routes) owned by a task that is not last in its phase, estimates of 4 hours or more with no three-point triple, a stated estimate more than 0.5 h from (O+4M+P)/6, a "done when" that is not verifiable, a phase with no non-goals or no contingency line, a story with no "so that", no command in the test strategy, an open question with no default.
- **INFO:** the critical path with its expected hours.
It cannot judge whether the scope is right, the estimates honest, the architecture sound or the risks the real ones. Pair it with a reader, and for a plan that will drive agents, a second reviewer who has not seen the plan.

## 2. Architecture decision records
- **ADR** (adr.github.io): one record captures a single architectural decision and its rationale; the collection is the decision log. Michael Nygard's 2011 article popularised it; the Y-statement format is suggested by Zdun et al. ("Sustainable Architectural Decisions"); MADR is the Markdown template family.
- **MADR 4.0.0 (2024-09-17).** Title; **Context and Problem Statement** (mandatory); Decision Drivers (optional); **Considered Options** (mandatory); **Decision Outcome** with the sentence "Chosen option: ..., because ..." (mandatory), optional Consequences and Confirmation under it; Pros and Cons of the Options (optional); More Information (optional). Bullets read "Good, because", "Bad, because", "Neutral, because". Optional YAML front matter: status, date, decision-makers, consulted, informed. Status is a placeholder list (proposed, rejected, accepted, deprecated, superseded by ADR-0123), not a closed set. Files: `NNNN-title-with-dashes.md` under `docs/decisions`.
- **Fowler (2026-03-24):** a short document, "a couple of pages", with the decision, its context, the alternatives with pros and cons, the consequences and the confidence level, plus **the product changes that should trigger reevaluation**; statuses proposed, accepted, superseded (link to the replacement); **never change an accepted ADR, supersede it**; one numbered file per record, kept in the source repository (commonly `doc/adr`); most important material first.
- Our playbook's ADR line (Context, Decision, Consequences, Alternatives) is the Nygard shape; adding "confidence" and "revisit when" costs one line and answers MADR's Confirmation and Fowler's reevaluation triggers.

## 3. Describing and shaping architecture
- **arc42** has twelve sections: Introduction and Goals; Constraints; Context and Scope; Solution Strategy; Building Block View; Runtime View; Deployment View; Crosscutting Concepts; Architectural Decisions; Quality Requirements; Risks and Technical Debt; Glossary.
- **C4** has four abstractions (software system, container, component, code) and four hierarchical diagrams (system context, container, component, code), plus supporting system landscape, dynamic and deployment diagrams; the site stresses it is notation- and tooling-independent. (Notation and tooling pages not read.)
- **Bounded context** (Fowler, 2014): a central DDD strategic pattern; one unified model per context; boundaries are usually drawn by human culture and the ubiquitous language; relationships are drawn as a context map. The DDD Reference page held only a PDF link, so the context-mapping pattern names (shared kernel, customer-supplier, conformist, anticorruption layer and so on) are **(unverified)** here.
- **Strangler fig** (Fowler, 2024): add small pieces beside the legacy code, split along seams, move behaviour across, build a transitional architecture you know will go away; the four activities are outcomes, breaking the problem up, delivering the parts, and changing the organisation to keep doing it.
- **Monolith First** (Fowler, 2015): start as a monolith (a carefully modular one if you can); microservices need good, stable boundaries that are hard to find early; he calls the opposing view "by no means unanimous". **Microservice prerequisites** (2014): rapid provisioning in hours, basic monitoring, a deployment pipeline of no more than a couple of hours, and a DevOps culture; more than a handful of services also needs cross-service tracing, continuous delivery and product-centred teams. A plan for a small team that proposes many services needs an ADR that answers these.
- **Well-architected pillars.** Azure (read 2026-09-11): Reliability, Security, Cost Optimization, Operational Excellence, Performance Efficiency. Google Cloud (read): Operational excellence; Security, privacy and compliance; Reliability; Cost optimization; Performance optimization; Sustainability, with AI and ML and Financial services as perspectives. The AWS pillars page returned 404: **(unverified)**.
- **Fitness functions** (Thoughtworks, 2019): "describe how close an architecture is to achieving an architectural aim"; examples with thresholds: test coverage above 90%, under 1% error rate for a new deployment, a transaction under 10 seconds, no PII in logs, no plaintext secrets, no known-CVE libraries, a runbook and health endpoint exist. They are automatable checks; put them in the plan's test strategy and the pipeline so the architecture does not drift silently.

## 4. Shape Up (Basecamp, read)
**Appetite** is "the amount of time we want to spend on a project, as opposed to an estimate": estimates start with a design and end with a number, appetites start with a time and end with a design ("fixed time, variable scope"). Small batch: one designer and one or two programmers for one or two weeks; big batch: six weeks. Cycles are six weeks followed by a two-week cool-down; the **betting table** meets during cool-down; a bet gives a team the whole six weeks without interruption; the **circuit breaker** cancels a project that does not ship in its cycle by default, with no automatic extension. A pitch lists Problem, Appetite, Solution, Rabbit Holes and No Gos (taken from the table of contents and glossary; chapters 6 and 14 were not read, so treat the pitch contents as **unverified**). Useful when the honest answer to "how long" is "as long as this is worth": plan to the appetite and cut scope, not the date.

## 5. Spec-driven development and agent-built plans
- **GitHub Spec Kit:** constitution (once per project, stored at `memory/constitution.md`), then specify, plan, tasks, implement, converge (repeat until it reports converged); output under `specs/<branch>/` (`spec.md`, `plan.md`, `research.md`, `data-model.md`, `contracts/`, `quickstart.md`, `tasks.md`); ambiguity is marked `[NEEDS CLARIFICATION: ...]` instead of guessed; independent tasks are marked `[P]`; its template gates include "at most 3 projects" for a first implementation, using framework features directly, and preferring real databases to mocks. The command spelling differs between its README (hyphens) and methodology page (dots).
- **Kiro specs:** `requirements.md` (or `bugfix.md`), `design.md`, `tasks.md`; tasks are run in waves from a dependency graph (wave 1 has no dependencies; tasks in a wave run concurrently). Whether it uses EARS notation is **not confirmed** from the page read.
- **Anthropic, "Building effective agents":** workflows are prompt chaining, routing, parallelization (sectioning or voting), orchestrator-workers (when subtasks cannot be predicted, for example multi-file coding changes) and evaluator-optimizer; use an agent only for open-ended problems; start with the simplest solution, "which might mean not building agentic systems at all"; measure before adding complexity; invest in tool design (give tools examples and clear boundaries, require absolute file paths).
- **Anthropic multi-agent research system:** an orchestrator-worker design where agents use about 4x the tokens of chat and multi-agent systems about 15x; the lead spun up 3 to 5 subagents in parallel; effort rules in the prompt (one agent with 3 to 10 tool calls for a simple fact, 2 to 4 subagents for a comparison, more than 10 for complex research); early agents spawned 50 subagents for simple queries; it suits breadth-first work with independent directions and fits coding less well because coding has fewer parallelisable parts. Give each subagent an objective, an output format, tool guidance and clear boundaries.
- **Claude Code plan mode:** read and propose, no edits until approved; `claude --permission-mode plan` or Shift+Tab. Detail page for editing the plan was not read.
- **Our rules 12 to 14 in `architect-playbook.md`** (PR-sized tasks with a verifiable done-when, a context scope per task, slice-versus-layer as a micro-decision) were already in the twin copy and are now in the main copy too; they came from earlier research and were not re-checked against the pages above.
