# Coder: research notes
2026-09-23

Scope: research for the CODER specialist of an advisory-only AI coding agent (PManagerProject nightrunner). The Coder
chooses/confirms language, framework and database, reviews for small diffs and tests-first, and checks a five-item
performance checklist plus an extended floor (caching, indexes, pagination, code-splitting, debounce, lazy load,
minification, connection pooling, pruned deps) — `src/specialists/knowledge/performance-checklist.md` and the
`coder` entry in `src/specialists/manifest.ts` (lines 136-160, checkpoints `start`/`middle`/`end`, prompt capped at
300 words). That existing checklist is entirely about the *product's* runtime performance. It currently says nothing
about the *coding session's own* token/time efficiency — how the Claude/Codex/Gemini agent doing the work should
behave so it doesn't burn context and money before it ever gets to the code. This file is the research base for
adding that second half: concrete, checkable rules for working efficiently as an agent, plus the code-structure and
product-performance material the existing checklist can be deepened with.

| https://nodejs.org/en/learn/modules/backpressuring-in-streams | "The golden rule of streams is to always respect backpressure": never `.push()` data a `Readable` hasn't asked for, and never call `.write()` again after it returns `false` — wait for `'drain'` first. `.write()` returns `false` exactly when the internal buffer has exceeded `highWaterMark`; ignoring that and continuing to write buffers the entire payload in memory instead of streaming it. The doc's own benchmark: piping a large file with backpressure respected held memory around 87.8 MB; the same transfer ignoring backpressure (attaching a raw `'data'` listener and calling `.write()` unconditionally) pushed memory to ~1.52 GB. `pipe()` and `stream.pipeline()`/`stream/promises.pipeline()` handle backpressure automatically and are the recommended default over manual `'data'`/`.write()` wiring. |

## Efficiency rules

Each rule states the check, the reason, and the source. These are for the Coder to apply both to *how the
nightrunner session should behave* while implementing a goal, and to *what "efficient" looks like* when reviewing a
transcript or diff.

1. **Grep/glob before you read; read a known region, not a whole large file.** Locate the exact file/line with `Grep`/`Glob` first; when the file is large, read with an offset/limit around the located line instead of the whole file. File reads are the single biggest context cost after startup (1,100-2,400 tokens per read in the documented example), and a vague task ("improve this codebase") is exactly what triggers the broad, expensive scan this rule prevents. *(code.claude.com/docs/en/context-window; code.claude.com/docs/en/costs — "write specific prompts")*

2. **Plan before multi-file or unfamiliar-code changes; skip planning for a one-sentence diff.** Explore → plan → implement → commit is the recommended arc, but it has real overhead — reserve it for uncertainty about approach, multi-file scope, or unfamiliar code. If the diff could be described in one sentence, do it directly. *(code.claude.com/docs/en/best-practices)*

3. **Give the work a self-runnable verification check (test, build, screenshot diff) instead of asserting "done."** Without a check the agent can run itself, "looks done" is the only signal, and every mistake waits for a human to notice; a runnable check closes the loop autonomously. This directly serves the Coder's own "tests first, code that builds and runs" mandate — the check IS the thing the Coder should be looking for in a transcript. *(code.claude.com/docs/en/best-practices)*

4. **One task per session; `/clear` between unrelated tasks, don't accumulate a "kitchen sink."** Stale, irrelevant context from a prior unrelated task is pure waste on every subsequent turn (it's resent, and often recached, every message) — clearing costs nothing, continuing to carry it costs tokens on every future turn. After two failed correction attempts on the same issue, prefer `/clear` plus a better initial prompt over a third correction. *(code.claude.com/docs/en/best-practices; code.claude.com/docs/en/costs)*

5. **Delegate research and other verbose, disposable work to a subagent; keep iterative/shared-context work in the main thread.** A subagent that reads 6,000+ tokens of files can return as little as ~400 tokens to the parent — that gap is the saving. Use the main conversation instead when the work needs frequent back-and-forth, when planning/implementation/testing share significant context, or when a cold-start subagent's latency isn't worth it for a quick change. *(code.claude.com/docs/en/sub-agents; code.claude.com/docs/en/context-window)*

6. **Route subagents (and disposable/high-volume work) to a cheaper model; keep the expensive model for the task that actually needs deep reasoning.** Sonnet-tier for most coding, Opus-tier reserved for complex architecture/multi-step reasoning, Haiku-tier for simple/high-volume subagent tasks. Model switches invalidate the prompt cache, so pick the model (and effort/thinking level) once per session rather than toggling. *(code.claude.com/docs/en/costs; code.claude.com/docs/en/prompt-caching)*

7. **Prefer diff/patch-style edits over whole-file rewrites.** Returning only the changed region costs proportionally to the size of the change, not the size of the file; a full-file rewrite for a two-line fix pays for the whole file twice (read + rewritten write) and is also where models are more likely to silently elide unchanged sections under some formats/models. *(aider.chat/docs/more/edit-formats.html)*

8. **Prefer CLI tools over MCP servers for the same job, and disable MCP servers you aren't using.** MCP tool schemas are deferred by default (only names enter context until first use), but a CLI tool (`gh`, `aws`, `gcloud`) costs nothing extra in context and Claude already knows how to drive it — an unused connected MCP server is pure listing overhead, and if its tools happen to be loaded into the prefix (not deferred), a server connecting/disconnecting is also a cache-invalidating event. *(code.claude.com/docs/en/costs; code.claude.com/docs/en/prompt-caching)*

9. **Keep CLAUDE.md/AGENTS.md under ~200 lines; move anything path-specific or occasional into rules/skills instead.** Every line in the always-loaded file is paid on every single turn, forever, for the whole session; a bloated file also measurably reduces instruction adherence, not just cost — the doc's own diagnostic is "would removing this line cause a mistake?" Codex's `AGENTS.md` has a hard 32 KiB combined ceiling (`project_doc_max_bytes`) before files silently stop loading — the practical fix in both ecosystems is to shard per-directory rather than grow one root file. *(code.claude.com/docs/en/memory; learn.chatgpt.com/docs/agent-configuration/agents-md)*

9a. **Detailed, occasional-use, or side-effecting workflow content belongs in a skill, not in CLAUDE.md — and the skill's own body should stay terse once written.** A skill's description (capped at 1,536 characters in the listing) is the only part paid on every turn; the full body is free until invoked, so a 2,000-word migration runbook costs nothing on the 99% of turns that don't touch migrations if it lives in a skill instead of the root file. But once invoked the body "stays there across later turns" as a recurring cost for the rest of the session, so write it as terse standing instructions, not a narrated walkthrough — the same conciseness bar as CLAUDE.md, just deferred until it's actually relevant. Give a skill with real side effects (deploy, commit-and-push, send a message) `disable-model-invocation: true` so it can't be auto-triggered and doesn't even cost description-listing tokens by accident. *(code.claude.com/docs/en/skills)*

10. **Don't change model, effort/thinking level, or fast-mode mid-task if it can be decided up front.** Each of those is a documented cache-invalidating event — the very next request re-reads the entire conversation with zero cache hits. Decide model and effort at session start; save a real `/compact` for a natural break between tasks, not a random mid-task moment. *(code.claude.com/docs/en/prompt-caching)*

11. **Use `/compact` for "keep going on the same task," `/clear` for "this is a new, unrelated task."** Compaction preserves continuity (a summary) at the cost of a full re-read on cold cache; `/clear` costs nothing and wipes everything, which is correct exactly when the old context has no future value. Auto-compaction fires automatically near the context limit — a manual `/compact <instructions>` at a natural checkpoint lets the agent control what's preserved instead of an automatic summary. *(code.claude.com/docs/en/costs; code.claude.com/docs/en/prompt-caching)*

12. **Offload noisy tool output before it reaches the model.** A hook that greps a build/test log for `FAIL`/`ERROR` and returns only matches turns tens of thousands of tokens of raw output into a few hundred — this is strictly better than reading the full log and mentally discarding the noise, because the discarded tokens were still paid for. *(code.claude.com/docs/en/costs)*

13. **Batch independent tool calls into one turn instead of issuing them serially.** Independent reads/greps/searches that don't depend on each other's output should be requested together — each serial round-trip both re-sends the growing prefix and adds latency for no benefit when the calls don't actually depend on one another. *(to verify — general agentic-tool-use practice; not confirmed against a fetched primary source in this pass)*

14. **Retrieve just-in-time; don't pre-load context "just in case."** Keep lightweight pointers (a file path, a grep result, a stored query) and resolve them via a tool call only when actually needed, rather than eagerly reading everything that might be relevant up front — this is the same principle rule 1 applies at the single-file level, generalized to the whole task. *(anthropic.com/engineering/effective-context-engineering-for-ai-agents)*

15. **Prefer the smallest system/tool surface that can do the job — fewer, non-overlapping tools beat a large toolbelt.** If it isn't obvious which of two available tools to use for a given step, that ambiguity costs the same reasoning tax for the agent as for a human reading the same two tool docs; trim overlapping tools/MCP servers rather than leaving them all connected "in case." *(anthropic.com/engineering/effective-context-engineering-for-ai-agents; anthropic.com/engineering/building-effective-agents)*

16. **Don't reach for an agent loop (multi-step, tool-calling, self-directed) when one well-crafted single call would do.** Classification, extraction, summarization and most single-file fixes are a single-call job; escalate to a full explore/plan/verify loop only when the task is genuinely open-ended or multi-file. Added agentic machinery is a deliberate trade of latency and cost for capability — pay it only when a simpler shape has already been tried or is clearly insufficient. *(anthropic.com/engineering/building-effective-agents)*

17. **Test incrementally — write one file, verify it, then continue — instead of writing everything and testing once at the end.** A wrong assumption caught after one file is a small, cheap correction; the same wrong assumption caught after ten files means re-doing or re-reasoning about all ten. *(code.claude.com/docs/en/costs)*

18. **In a genuinely unfamiliar or exploratory task, scope the investigation narrowly or hand it to a subagent — never issue an unscoped "investigate X."** An unscoped investigation has no natural stopping point and will read as many files as it can justify; a scoped one ("check how session timeout is handled in src/auth/") has an implicit budget. *(code.claude.com/docs/en/best-practices — "the infinite exploration")*

19. **Tune thinking/effort down for simple tasks instead of leaving deep reasoning on by default.** Extended thinking is on by default because it measurably helps complex planning, but thinking tokens bill as output tokens and the default budget can run to tens of thousands of tokens per request — for a simple, well-specified task, lower the effort level (`/effort`, or in `/model`) or, on fixed-thinking-budget models, cap it with `MAX_THINKING_TOKENS` (e.g. `MAX_THINKING_TOKENS=8000`). On adaptive-reasoning models a nonzero fixed budget is ignored, so use effort levels there instead of the environment variable. Some current top-tier models (Opus 5.5, the Fable line) can't disable thinking at all — effort is the only lever left on those. *(code.claude.com/docs/en/costs — "Adjust extended thinking")*

20. **For repetitive or fan-out work across many files, script the loop instead of doing each file as a separate interactive turn.** Non-interactive mode (`claude -p "prompt" --output-format json`) makes results parseable and scriptable; looping a shell script over a file list with `--allowedTools` scoped down is documented as the pattern for large migrations (test on 2-3 files, refine the prompt, then run the rest) — each invocation starts its own clean, small context instead of one giant session accumulating every file's diff. *(code.claude.com/docs/en/best-practices — "Fan out across files")*

## Efficient vs. inefficient prompts (worked examples)

Pulled directly from the best-practices doc's own before/after table — useful as calibration for what "specific enough to avoid a broad, expensive scan" looks like in practice:

| Strategy | Inefficient | Efficient |
|---|---|---|
| Scope the task | "add tests for foo.py" | "write a test for foo.py covering the edge case where the user is logged out. avoid mocks." |
| Point to a source instead of asking the agent to guess | "why does ExecutionFactory have such a weird api?" | "look through ExecutionFactory's git history and summarize how its api came to be" |
| Reference an existing pattern instead of triggering an open-ended search for one | "add a calendar widget" | "follow the pattern in HotDogWidget.php to implement a new calendar widget... build from scratch without libraries other than the ones already used in the codebase" |
| Name the symptom, likely location, and what "fixed" means | "fix the login bug" | "users report login fails after session timeout. check the auth flow in src/auth/, especially token refresh. write a failing test that reproduces the issue, then fix it" |

Each "efficient" column entry does two things at once: it narrows what the agent has to read (rule 1), and it gives the agent something to verify against (rule 3) — the two highest-leverage rules in this file are both just consequences of a specific prompt. *(code.claude.com/docs/en/best-practices)*

## Quick-reference tables

### Cache-safe vs. cache-invalidating actions mid-session

| Cache-invalidating (costs a full, uncached re-read) | Cache-safe (appends to the existing prefix) |
|---|---|
| Switching models (`/model`) | Editing files in the repository |
| Changing effort/thinking level (most models) | Editing CLAUDE.md mid-session (just doesn't apply until `/clear`/`/compact`/restart) |
| Turning fast mode on for the first time in a session | Changing permission mode |
| Connecting/disconnecting an MCP server whose tools load into the prefix (not deferred) | Changing output style |
| Denying a whole tool when tool-search is off | Invoking skills and commands |
| `/compact` (by design — replaces history with a summary) | `/rewind` (truncates back to an already-cached prefix) |
| Accumulating past the image/PDF request cap | Spawning a subagent (parent's prefix is untouched) |
| Upgrading the CLI itself | Running `/recap` |

Source: code.claude.com/docs/en/prompt-caching. Practical use: before advising "switch to Opus for this part," weigh the one-time full re-read against the actual gain — worth it for a hard step, wasteful for a habit of toggling models per message.

### Model tier by task shape

| Task shape | Recommended tier | Why |
|---|---|---|
| Most coding: implementing, fixing, refactoring within a clear spec | Sonnet-tier | Balances capability and cost for the majority of coding work |
| Complex architectural decisions, multi-step reasoning, ambiguous requirements | Opus-tier (or top-tier) | The task where deeper reasoning demonstrably changes the outcome |
| Disposable/high-volume subagent work (grep-and-summarize, log triage, simple mechanical edits) | Haiku-tier (`model: haiku` in subagent config) | Cheapest tier that can still do the narrow job; isolated context means a weaker model's mistakes don't pollute the main thread |
| Simple, well-specified single-file task | Lower effort on the default tier, not necessarily a smaller model | Effort-level tuning (rule 19) is often the cheaper lever than a full model downgrade |

Source: code.claude.com/docs/en/costs ("Choose the right model"); code.claude.com/docs/en/sub-agents ("Model Selection for Cost Control").

### CLAUDE.md vs. rules vs. skills vs. subagents — where should this instruction live?

| Mechanism | When it loads | Token cost profile | Use for |
|---|---|---|---|
| CLAUDE.md / AGENTS.md (root) | Every session, unconditionally | Recurring, every turn, for the whole session | Facts true in every session: build/test commands, conventions that differ from defaults, project-wide gotchas |
| `.claude/rules/*.md` with `paths:` frontmatter | Only when Claude reads a matching file | Recurring only while working in that area | Directory- or filetype-specific conventions (e.g. API-layer rules that only matter in `src/api/**`) |
| Skill (`SKILL.md`) | Only when invoked (by the model or by `/name`) | Description: small, every turn. Body: zero until invoked, then recurring for the rest of the session | Detailed, occasional, or side-effecting workflows (migrations, deploys, a multi-step review procedure) |
| Subagent | Only when explicitly delegated to | Runs in its own isolated context; only its final summary re-enters the parent | Verbose/disposable research, isolated tool permissions, work whose intermediate output the parent will never need again |

Decision shortcut: if it's true every session regardless of what's being worked on → CLAUDE.md. If it's true only for files matching a pattern → a scoped rule. If it's a whole procedure invoked occasionally → a skill. If it's read-heavy work whose raw output nobody needs kept around → a subagent. *(code.claude.com/docs/en/memory; code.claude.com/docs/en/skills; code.claude.com/docs/en/sub-agents)*

## Code structure

Structure choices that make an agent (any of Claude Code, Codex, Gemini CLI) cheaper and more accurate to work with,
distinct from the session-behavior rules above:

- **Small, single-purpose files with descriptive names.** Aider's repo map extracts each file's "most important" symbols by how often they're referenced elsewhere — in a large, multi-purpose file those signals get diluted by noise, so the map (and by extension any agent doing symbol-level navigation) is measurably worse at telling the model which file to open. A file named for what it does (`user_authentication.py`) is doing part of the agent's job for it before a single token is read. *(aider.chat/docs/repomap.html)* This matches the project's own standing rule (`C:\Users\gaura\.claude\rules\ecc\common\coding-style.md`, "File Organization": 200-400 lines typical, 800 max, organize by feature not type) and the extended performance checklist's own file-size guidance already in `src/specialists/knowledge/performance-checklist.md`.

- **Explicit, typed function/method signatures.** The repo map conveys behavior through "the critical lines of code for each definition" — an untyped or vaguely-named signature forces the agent to open the implementation to learn what the map should have told it for free, which is an extra file read (context cost) for information that a signature could have carried. *(aider.chat/docs/repomap.html)*

- **Split by seam, not by size alone.** A file at exactly 799 lines that mixes two unrelated responsibilities is worse for an agent than two 400-line files, because the agent has to read the whole file to find the part it needs even when only one responsibility is relevant to the task at hand — the point of a size limit is really a proxy for "one clear responsibility per file, so a targeted read stays targeted."

- **`AGENTS.md`/`CLAUDE.md` should be operational, not explanatory.** Both ecosystems converge on the same shape: commands the agent can't discover by reading code (build, test, lint, deploy), conventions that differ from language defaults, and repo-specific gotchas — never a narrative walkthrough or content the agent can derive by reading the code itself. Anything that reads like a README belongs in the README, and anything path-specific belongs in a scoped rule, not the always-loaded file. *(code.claude.com/docs/en/memory; learn.chatgpt.com/docs/agent-configuration/agents-md; developers.openai.com/codex/learn/best-practices, via search)*

- **Tests are the executable spec an agent should check itself against.** The best-practices doc's core loop — give Claude something that returns pass/fail and let it iterate against that instead of asserting "done" — only works if the tests actually encode the requirement (edge cases named, not just a happy-path smoke test). A vague spec plus a thin test suite means "the check passed" and "the goal was met" silently diverge. *(code.claude.com/docs/en/best-practices; general TDD principle — no single fetched primary source pinned this exact framing, treat as (to verify) beyond the verification-loop point above)*

- **Keep the module boundary and the file boundary aligned.** When a logical boundary (e.g., a repository/service interface) spans many small files, an agent doing a task inside that boundary should be able to `grep` for the interface and find every implementer without having to read unrelated modules — this is the same "clear boundaries" concern the project's own coding-style rules already state for humans, and it applies at least as much to an agent's grep-first workflow (rule 1 above).

- **Treat internal scripts/CLIs the same way a well-designed tool-call interface is treated: documented, unambiguous, and hard to misuse.** "Building effective agents" makes the case for investing in agent-computer interfaces at the same level of effort as human-facing UX — example usage, edge cases, and input-format requirements documented for every tool. The same argument applies to a project's own internal CLI scripts and npm/make targets: an agent (or a human) that can't tell which of two similarly-named scripts to run for a given job pays a reasoning tax every time, and a project with self-documenting, non-overlapping scripts is cheaper for every future session to work in, not just the current one. *(anthropic.com/engineering/building-effective-agents)*

- **A project's own repo map quality is a leading indicator, not just a nice-to-have.** Aider's repo map is a proxy for a broader truth: any tool that helps an agent decide which file to open without opening it first (symbol indexes, `ctags`, an IDE's language server, a well-maintained top-level `README` with a directory-purpose table) pays for itself on every subsequent task in the same repo. A coder review of a new/unfamiliar project can reasonably ask "how would an agent figure out which file to touch here, without reading everything?" as a structural health check. *(aider.chat/docs/repomap.html)*

## Performance additions

Additions to deepen `src/specialists/knowledge/performance-checklist.md`'s five items and extended floor, backed by
primary docs:

- **Ship against numeric Core Web Vitals targets, not "make it feel fast."** LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1, measured at the 75th percentile across mobile+desktop. The checklist's existing "lazy-load below-fold content," "no unnecessary re-renders," and "compress images" items are all in direct service of these three numbers — a coder review can ask "does this change move LCP/INP/CLS in the wrong direction?" as a concrete test instead of a vibe. *(web.dev/articles/vitals)*

- **React: re-renders are triggered only by (a) initial mount or (b) a state update in the component or an ancestor, and the cascade continues through whatever JSX is returned.** So the fix for "unnecessary re-renders" is always one of: don't lift state higher than it needs to be (fewer ancestors re-render), or memoize a genuinely expensive subtree — but only once a real problem is observed, not preemptively. React itself only patches DOM nodes that actually changed between renders, so the re-render itself isn't automatically the DOM-write cost; the checklist's "setState per animation frame" item is the case where the *re-render* itself is the expensive step because it happens 60 times/second. *(react.dev/learn/render-and-commit)*

- **Node.js: never call a `*Sync` API, a full `JSON.parse`/`stringify` on a large/untrusted payload, or an unbounded/O(n²) loop inside a request handler.** A 50MB JSON payload measured 1.3 seconds of fully blocked event loop in the primary doc's own benchmark — during that time the whole server is unresponsive to every other client, not just the one making the big request. This generalizes the checklist's existing "no blocking UI updates" item to the server side: the same "don't do synchronous heavy work on the one thread that serves everyone" principle applies to Node's single event loop as much as to a browser's main thread. Regex with nested quantifiers is a ReDoS vector with the same blocking effect, worth its own line in the checklist given how easy it is to write by accident (a bad email/path regex). *(nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)*

- **Database indexing has a decision rule, not just "add an index":** index columns used in `WHERE`/`JOIN` predicates; order multi-column indexes filter-columns → sort-columns → output-columns (a covering index can let the query answer entirely from the index, skipping the table read); never keep an index that's a strict column-prefix of another one; drop indexes that no query actually uses, because every index adds a write-time cost to every `INSERT`/`UPDATE`/`DELETE` even when it never helps a read. On Postgres specifically, index *creation* blocks writes on the table until it finishes (reads are unaffected) — worth flagging if a coder proposes adding an index to a live, high-write table without a concurrent-build option. *(postgresql.org/docs/current/indexes-intro.html; sqlite.org/queryplanner.html)*

- **SQLite: run `ANALYZE` after creating indexes.** Without it the query planner is choosing based on index existence alone, not real selectivity — for a schema the coder just added indexes to, this is a one-line, essentially free follow-up that the checklist should name explicitly since it's easy to forget and has no equivalent "obviously missing" signal the way a missing index does. *(sqlite.org/queryplanner.html)*

- **Stream large file/network I/O instead of buffering it whole; always respect backpressure.** The measured cost of getting this wrong is not abstract: the primary doc's own benchmark shows ~87.8 MB of memory when a large file transfer respects `.write()`'s `false` return value and waits for `'drain'`, versus ~1.52 GB for the same transfer done by attaching a raw `'data'` handler and writing unconditionally — an ~17x memory blowup from one missed check. Default to `pipe()` or `stream.pipeline()`/`stream/promises.pipeline()` over manual stream wiring; they handle backpressure automatically. This is the same principle as the checklist's existing "stream or paginate a large SSR payload" item, generalized to any large read/write path (file uploads, proxied responses, log processing), not just SSR. *(nodejs.org/en/learn/modules/backpressuring-in-streams)*

## Measurable signals

Concrete things the Coder specialist can actually check in a project's files or a transcript, without having to
infer intent:

**Session/token efficiency (new — not currently in the checklist):**
- CLAUDE.md / AGENTS.md line count — flag over ~200 lines (root file); flag a project relying on one giant file instead of path-scoped rules or skills.
- Any file read in the transcript that reads an entire large file (hundreds+ lines) when the task only concerned a few lines of it, especially without a preceding grep/glob narrowing the target.
- Whole-file rewrites in the diff where the actual change is a handful of lines — a sign the session is doing expensive rewrite-edits instead of patch-style edits.
- A single long, uncleared session spanning multiple unrelated goals (visible as topic drift in the transcript) instead of `/clear` boundaries between them.
- Subagents used (or not used) for research-heavy steps: a main-thread transcript full of many raw file reads and grep dumps for pure investigation, with no subagent delegation, is the "infinite exploration" pattern.
- Model tier mismatches: Opus (or equivalent top-tier) used for a trivial, mechanical subagent task; or a cheap model used for a task that actually needed deep multi-step reasoning.
- Repeated corrections on the same point (3+ back-and-forth turns on one issue) without a context reset — the "correcting over and over" pattern.
- MCP servers configured/connected but never invoked in the session — pure listing overhead paid every turn for nothing used.
- Presence (or absence) of a runnable verification step (test command, build command, screenshot diff) the agent actually ran before declaring the task done, versus an unverified "done" assertion.
- Detailed/occasional workflow instructions (migration runbooks, deploy steps, one-off procedures) written directly into CLAUDE.md/AGENTS.md instead of a skill — every such paragraph is a recurring per-turn cost that a skill would make free until actually needed.
- A skill whose body reads as a narrated explanation ("first we do X because Y, then...") rather than terse standing instructions — once invoked it's a recurring cost for the rest of the session, so verbosity there compounds the same way CLAUDE.md bloat does.
- A side-effecting skill (deploy/commit/notify) without `disable-model-invocation: true`, i.e. it can be auto-triggered by the model rather than only by explicit human invocation.

**Product performance (extends the existing checklist):**
- Any `JSON.parse`/`JSON.stringify` call site handling a payload whose size isn't bounded (user upload, unpaginated DB result) inside a request handler.
- Any `*Sync` Node.js core-module call (`fs.*Sync`, `child_process.*Sync`, `crypto.pbkdf2Sync`, `zlib.*Sync`) reachable from a request path.
- A regex with nested quantifiers or overlapping alternation (`(a+)*`, `(a|a)*`) applied to untrusted/user-controlled input.
- A `WHERE`/`JOIN` column with no supporting index on a table large enough to matter; conversely, two indexes where one's columns are a strict prefix of the other's (redundant).
- A React list rendered without a stable `key`, or a component re-rendering on every keystroke/frame without memoization once profiling shows it's actually the bottleneck (don't flag pre-emptive non-memoization as an issue — the docs explicitly warn against premature optimization).
- No Lighthouse/Core Web Vitals number cited for a UI-facing change that plausibly affects LCP/CLS (new above-fold images/fonts, layout that shifts on load).
- A write loop issuing one `INSERT`/`UPDATE` per row instead of a batched statement or a single transaction (already in the existing checklist — keep, it's directly load-bearing given the Postgres/SQLite findings above).

## Distilled checklist

For quick use against a transcript, diff, or project at the Coder's start/middle/end checkpoints:

**Session efficiency**
- [ ] Grep/glob located the target before any large file was read in full
- [ ] Large files read with a scoped region (offset/limit), not wholesale, when only part was relevant
- [ ] Plan mode (or equivalent) used only for multi-file/uncertain work, skipped for one-line diffs
- [ ] A runnable check (test/build/screenshot) exists and was actually run, not just asserted
- [ ] `/clear` (or session boundary) used between unrelated tasks; no visible topic-drift accumulation
- [ ] Research/investigation delegated to a subagent when it would otherwise flood the main context
- [ ] Model tier matches task difficulty (cheap model for disposable/mechanical work, top tier reserved for real reasoning)
- [ ] No mid-task model/effort/fast-mode switching without a reason (cache-invalidating)
- [ ] Diffs are patch/edit-style, not whole-file rewrites, for small changes
- [ ] CLAUDE.md/AGENTS.md is operational (commands, conventions, gotchas) and under ~200 lines; path-specific detail lives in scoped rules/skills instead
- [ ] MCP servers connected are actually used; CLI tools preferred where both exist
- [ ] No unscoped "investigate/explore X" without a narrowed target or subagent delegation
- [ ] Occasional/detailed workflow content lives in a skill (loaded on demand), not in the always-loaded CLAUDE.md/AGENTS.md
- [ ] Side-effecting skills (deploy, commit-and-push, notify) are marked so they can't be auto-invoked by the model alone
- [ ] Large file/network I/O in the product code streams (and respects backpressure) instead of buffering the whole payload in memory

**Product performance (existing + additions)**
- [ ] No uncompressed large JSON over the wire; only needed fields sent
- [ ] No per-row write loop; batched/transactional writes; parameterized queries
- [ ] Indexes on every `WHERE`/`JOIN` column that matters; no redundant prefix-indexes; `ANALYZE` run after adding indexes (SQLite)
- [ ] No heavy/unused dependency added for a small job
- [ ] No synchronous/blocking work on the UI thread or the Node.js event loop (`*Sync` APIs, unbounded JSON parse, catastrophic regex, unbounded O(n²) loops)
- [ ] No duplicated server+client fetch of the same data; independent fetches run in parallel, not sequentially
- [ ] Long lists virtualized; large SSR payloads paginated/streamed
- [ ] Core Web Vitals plausibly unaffected or improved for UI-facing changes (LCP ≤2.5s, INP ≤200ms, CLS ≤0.1 as the target frame, not a rule to cite verbatim in every review)
